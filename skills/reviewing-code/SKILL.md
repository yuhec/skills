# Reviewing code

Find what is wrong or worse than it should be in a change, prove each finding against the code,
and report it so it can be acted on. **Report-only unless the mode is `fix`.**

## Modes

| Mode | Lenses | When |
|---|---|---|
| `quick` | correctness, security | a small diff, an iteration, "jette un œil" |
| `full` (default) | all lenses + ticket context | before a PR, a branch review |
| `adversarial` | `full` + a Codex second opinion | high-risk changes (security, data, migrations, wide refactors), or when asked |
| `fix` | `full`, then apply the safe fixes | "review et corrige" |

Pick the mode from the request; say which one you ran on the first line of the report.

## Step 1 — Scope

- **Target**: uncommitted changes (`git status --porcelain` non-empty and no target given), the
  current branch, another branch, or a PR (`gh pr diff <n>`, `gh pr view <n> --json baseRefName,headRefName`).
- **Base**: the PR base, else the base named in the project rules, else the default branch
  (`gh repo view --json defaultBranchRef -q .defaultBranchRef.name`). `git fetch origin <base>` first.
- List the files: `git diff --name-status origin/<base>...<head>` (plus `git diff --name-status`
  for uncommitted work). A stacked branch is reviewed against its parent branch, not the default.

## Step 2 — Context

Read, if they exist, and apply in this order of precedence (highest first):

1. **`.claude/review-preferences.md`** — the developer's personal, learned review preferences.
2. **`.claude/review-rules.md`** — the project's review rules (generated by `init-skills`): base
   branch, how to load the ticket, generated artifacts, test conventions, known abstractions.
3. The project's agent rules (`CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md`) and `CONTRIBUTING.md`.

In `full` and above, load the **ticket**: derive its id from the branch name or commit messages,
fetch it the way the project rules say (its parent and siblings too). What it changes:

- A decision recorded in the ticket or its parent's refinement is **settled**: do not reopen it.
  A diff that contradicts it **is** a finding — cite the decision.
- Work assigned to a sibling is not missing from this diff; a symbol with no caller yet is expected
  when the next ticket calls it.
- Acceptance criteria of this ticket the diff does not meet are findings.
- An open question the ticket left to someone else, silently settled in code, is a finding.

No ticket found or unreachable → one line at the top of the report, and continue.

## Step 3 — Read

Read every changed file **in full** (not only the hunks) — design and layering cannot be judged from
hunks. Generated artifacts (API schemas, generated clients, lockfiles, changelogs owned by a release
tool) are read **as a diff only**: check that they are coherent with the source change (a route
change came with its regenerated schema; a manifest change with its lockfile), never re-generate
them (that would dirty the tree).

## Step 4 — Run the lenses

Each lens is a file in this skill's `references/lenses/`. Read the lenses the mode needs and apply
them. For a diff over ~15 files or ~800 changed lines, run the lenses as **parallel read-only
subagents**, each given the lens file, the file list, the base, and the context from Step 2; you
keep the synthesis.

| Lens | File | Looks for |
|---|---|---|
| Correctness | `references/lenses/correctness.md` | bugs, edge cases, error handling, async, data compatibility |
| Reuse & design | `references/lenses/reuse-design.md` | the diff vs the wider codebase: duplication, ignored abstractions, layering, types, patterns |
| Quality | `references/lenses/quality.md` | SOLID, clean code, naming, cleanup, framework specifics |
| Tests | `references/lenses/tests.md` | coverage of the behaviour change, test conventions |
| Security | `references/lenses/security.md` | injection, authz, validation, secrets, sensitive data |

`adversarial`: also follow `references/codex-adversarial.md`.

## Step 5 — Verify every finding

Before anything reaches the report, re-open the cited lines **at the reviewed head** and confirm the
claim holds: the bug path is reachable, the "existing helper" really does the same thing, the
"missing test" is really missing. Then:

- confirmed → keep;
- the smell is real but the consequence is not → keep, downgraded, say which part holds;
- not confirmed → drop it. A wrong finding costs more attention than a missed nit.

Merge duplicates raised by several lenses (and by Codex): agreement between independent reviewers
raises confidence, say so.

## Step 6 — Report

In the user's language. First line: mode, branch → base, verdict (**Prêt** / **Prêt avec
remarques** / **À corriger**). Then:

```markdown
## Résumé
<1–2 lines>

## 🔴 Critique — bloque le merge
- **[Catégorie]** `path/file.py:42` — <what is wrong and why it matters>. Correction : <concrete fix, real symbols>. (<lens>, <Claude/Codex/both>)

## 🟡 À corriger
- …

## 🟢 Suggestions
- …

## ✅ Bien fait
- <2–3 concrete things done well>
```

- Categories: `Correctness`, `Security`, `Reuse`, `Generalization`, `Pattern`, `Boundary`, `DI`,
  `SRP`/`OCP`/`LSP`/`ISP`/`DIP`, `Types`, `Style`, `Test`, `Ticket`.
- `Reuse`/`Generalization`/`Pattern` findings **must** cite the existing code to converge on
  (`reimplements extract_attrs in app/x/engine.py:88`).
- Severity: correctness, security, boundary/DI violations and unmet acceptance criteria →
  🔴/🟡; reuse, design, test conventions → 🟡/🟢. Never inflate.
- Nothing found → say so in one line. Do not invent issues.
- Design choices that are a judgment call are listed under a final **À trancher** section, each as a
  question with a recommendation — never silently applied.

## Step 7 — `fix` mode only

Apply the confirmed findings whose fix is mechanical or unambiguous (a missing await, a swallowed
error, a duplicate helper replaced by the existing one, a test renamed to the convention). Then run
the project's fast gate. **Ask before** any fix that changes a design, a public contract, or a test's
expectation. Report what was applied, what was left, and the gate result.
